# What changed from the first plan (and why)

The first plan (the `dev-plans` zip) was strong on logistics and thin on mechanisms. This kit keeps its structure (three tracks, phases, integration checkpoints) and fixes the problems below.

## Problems you asked me to fix

| Problem in v1                                                                                                     | Fix in this kit                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| About 75 placeholder stubs (`{ ... }`) in code and tests                                                          | Contracts, scaffold, golden traces and test builders are **real, compiling code** (17 passing tests). Cards for the core logic (config, money, simulator, store, proxy, invariants, score, verify loop, reference patches, orchestrator, prescribe, firewall, policy, API contract suite, hardening) contain **full test code**. Cards for UI and DevOps give exact assertions instead of full test code; agents write those tests from the list. `AGENTS.md` forbids placeholders, skipped tests and empty test bodies. |

## Problems I found while writing it

1. **I-01 could never fail on real PayPal.** The old invariant was "one capture per order", but PayPal rejects a second capture of an order. The real double-charge bug is **two orders for one cart**. I-01 is now "one successful capture per **cart** (`custom_id`)", and B1 is a double click that creates two orders.
2. **The score formula floored at 0.** With 25/15/8/3 points the planned demo could not show "before 31". New weights (10/6/3/1, once per distinct invariant) give 61 for the five merchant bugs and 39 for everything.
3. **LLM-written unified diffs are brittle** (wrong hunk numbers). Patches are now **exact-string edits** (`search` must occur once); the diff is derived for display and PRs.
4. **Git worktrees were unnecessary.** Verification now uses a temp copy of the store inside `.payclinic-tmp/` (so `node_modules` resolves), applies edits, starts the store, re-runs the scenario, and deletes the copy.
5. **Everything depended on the real sandbox.** The kit adds a **deterministic PayPal simulator** so tests, CI, offline mode, the verify loop and the demo run with no network and no keys. The real sandbox is "online mode" on the same code path.
6. **The riskiest automation was one line** (`approveBuyer`). It is now a `BuyerApprover` interface with `sim`, `manual`, `playwright` and `card` implementations, chosen by spike S2. A failed spike costs nothing offline.
7. **Agent behavior was nondeterministic.** Three brains: scripted (CI/default), recorded LLM transcript, live LLM. A2 is redefined as a runaway-loop bug that produces duplicate purchases deterministically.
8. **Bugs overlapped in files**, so reference patches would conflict. Each planted bug now lives in its own file and all five patches apply together (tested).
9. **B5 "float math"** was invisible after `toFixed(2)`. B5 is now the real zero-decimal-currency bug (JPY sent as `2400.00`).

## Honest limits of this kit

- Only the scaffold and contracts were executed (typecheck, lint, format, 17 tests). The rest is a **design with tests-first cards**; expect normal friction when agents implement it, and use the "stop and report" rule.
- The PayPal simulator mirrors the shapes we use, simplified. Real sandbox behavior is verified by spikes S1, S2, S5 and the online-recording card.
- Gemini model names and limits change; they are read from `.env` and checked in spike S3.
- Sponsor prize requirements and Devpost rules must be read by a human (spike S0).
